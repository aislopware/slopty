# Knowledge distillation: slop-desk → Slopty

Source: slop-desk (Rust core + Swift/AppKit/UIKit shell, ~225k lines Rust / ~220k Swift at increment 83). Target: Slopty, pure Rust + GPUI, macOS/iOS. This is a knowledge transfer, not a code transfer — file paths below are for follow-up reading in slop-desk, none of them exist in Slopty.

---

## 1. Terminal engine: libghostty-vt from Rust

### What it is, and why it replaced the full ghostty surface

slop-desk's terminal went through two eras. Era 1 embedded ghostty's **full surface** (`ghostty_surface_new/draw`, its own Metal renderer, its own IO thread) via a maintained fork (`ThirdParty/ghostty`) with a 641-line `build-libghostty.sh`, an `xcrun` SDK shim and a `.toolchain/` download pinning Zig 0.15.2. That surface is opaque: `ghostty_surface_draw` composites the *whole grid* into one layer, so an embedder can only paint decoration on top (a row-anchored flash, an underline) — never real layout. `docs/68-terminal-surface-in-rust.md` §2 states the discriminating fact plainly: **the ceiling is not performance, it's who owns layout.** A block-based, Warp-like terminal (collapsible command output, variable-height rows, a native action bar between two blocks) needs the grid *in the host application*, not behind an opaque draw call.

Era 2 (`docs/68`) deletes that whole surface and takes **`libghostty-vt`** — the "renderer-agnostic half" of ghostty, shipped as MIT Rust bindings — which does parsing, grid maintenance and scrollback but deliberately "leaves pixel-pushing to the host application." The client now holds the grid and draws it itself, so a block becomes an ordinary layout problem instead of an unreachable one.

### Build integration: Zig from Rust, with a hard "no network at build time" rule

`libghostty-vt-sys`'s `build.rs` drives **Zig directly** (not a shell script) and emits `cargo:rustc-link-lib=static=ghostty-vt`, statically linking `libsimdutf.a` and `libhighway.a` alongside it. Verified cross-compiling to iOS: `cargo build --target aarch64-apple-ios` (3m55s) and `--target aarch64-apple-ios-sim` (56s) both produced a valid `arm64` static archive (`lipo -info`) tagged `LC_BUILD_VERSION platform 2 (iOS) minos 13.0` via `otool -l`. **No hand-maintained build recipe survives the port** — the 641-line script, the xcframework recipe, the toolchain downloader and the SDK shim are all deleted.

By default `libghostty-vt-sys`'s `build.rs` **clones ghostty over the network at compile time**, which is incompatible with reproducible, offline, content-addressed builds. The escape hatch is `GHOSTTY_SOURCE_DIR`: if set, the crate builds from that vendored tree instead of fetching. slop-desk exports it through `rust/.cargo/config.toml`'s `[env]` table (with `relative = true`, so it survives being invoked by `cargo` directly and not only through a task runner), and the ghostty source itself is a **fourth kind of entry** in a general third-party lockfile (`ThirdParty/tools/tools.lock`): a `git` kind, pinned by the 40-hex commit SHA rather than a tarball digest, because GitHub-generated archives are not guaranteed byte-stable while a git clone is content-addressed over the whole tree. A provisioning step clones with `init` + `fetch --depth 1 <sha>` + `checkout FETCH_HEAD` and then asks the resulting clone what commit it landed on, rather than trusting the pin blindly. A lint rule (`engine-source-read-at-its-pin`) holds the lockfile's digest and the config's env var in lockstep, because bumping one without the other silently keeps compiling the old tree against a "provisioned" newer one.

**Commit pins, exact:**
- Rust bindings crate: `aislopware/libghostty-rs @ 5988a0b7` (an org mirror fast-forwarded onto upstream `uzaaft/libghostty-rs`'s master on 2026-09-02, byte-identical to it — for one day it briefly diverged for a soundness fix that was later upstreamed as PR #81 and closed as issue #75, then the fork's local patch was dropped entirely since the fix landed upstream).
- Ghostty engine itself, at that bindings revision: **`22d13172`** — recorded in `ThirdParty/tools/tools.lock`'s `ghostty` entry and in `libghostty-vt-sys`'s own `const GHOSTTY_COMMIT` string; these two must always agree (`engine-pin-agree` lint), because the Rust bindings are *generated* against that exact ghostty tree.
- The measured-throughput harness in §6.2 used an earlier tag, `rev = "a0b5a46"`, five commits behind the live pin (a clipboard-soundness fix + its Miri reproducers + a Windows link-name fix + a CI job) — none of which touched the parser path the benchmark exercised.

Zig itself is pinned at **0.16.0** (the machine's system `zig`), deliberately *not* upgraded to 0.16 for the old fork (that would have been a 462-file breaking migration touching `std.ArrayList`, "Writergate", `EnvMap` that upstream itself hadn't done on macOS). Deleting the fork sidestepped the migration instead of doing it.

### FFI surface actually used

From `libghostty_vt`, slop-desk's wrapper crate (`slopdesk-vterm`) drives: `Terminal::new(cols, rows)` / `vt_write` for feeding bytes; `RenderState` with **per-row damage bits** for dirty tracking; per-cell `Style`/`sgr` (including `StyleColor::{None, Palette, Rgb}` for underline colour — falsifying an earlier ruling that "no C ABI exposes cell colour"); a richer **selection** API (`Gesture` for click-drag, `select_word`, `select_line`, `select_output`, `select_word_between`, rectangle selection, `format_selection`, and `SelectLineOptions::with_semantic_prompt_boundary` which is OSC-133-aware); `KeyEncoder`/`MouseEncoder`; `osc.rs` (OSC 22 pointer, OSC 52 clipboard); bracketed `paste.rs`; `focus.rs`; the full kitty-graphics storage/placement model (with a PNG-decode hook, since the bindings' own bundled `RustPngDecoder` was buggy — `next_frame` handed back a `Vec` with capacity but no length, so a custom decoder was installed through the hook instead); `unicode.rs` widths; `compress()` (idle scrollback compression, ghostty's own algorithm, 10–30% of uncompressed page memory on text-heavy history); `continuation_*` session serialization; and `libghostty_vt::fmt::Formatter`, which renders the whole active screen by an *independent* code path (ghostty's `Screen` rather than its `RenderState`) — this becomes the conformance oracle (below). Two engine-side callback sinks are drained rather than pushed: a bounded pty-reply queue (`CSI 6n`, `CSI c`, `CSI > q`, OSC 10/11/4 queries, in-band size reports — dropped whole if not drained, since half an escape sequence is worse than silence) and a bounded clipboard-write queue (evicts oldest).

### What was missing and had to be built on top

Everything genuinely renderer-shaped, listed as "ours" in `docs/68` §4/§5:
- **Glyph rendering entirely** — Core Text font stack + fallback, shaping (vt gives only cell widths via `unicode.rs`; shaping stays Core Text's), glyph atlas + Metal pipeline, damage-driven redraw (cheap, because `RenderState::dirty()` already names the changed rows), cursor shapes/blink, underline variants, selection highlight, marked-text/IME preedit drawing (drawn, never fed to the engine — an IME can replace a whole composed run on the next keystroke), scrollbar geometry, padding/content-scale/cols×rows sizing.
- **Grid search** — vt exposes *no search at all*; the whole matcher (`rust/slopdesk-vterm/src/search.rs`) is hand-written, covering all four fzf-style modes (regex, case-sensitive, whole-word, plain).
- **The key encoder and mouse encoder wrapper** — `KeyEncoder`/`MouseEncoder` exist in vt, but the *shape of the press* (what text, what `consumed_mods`, what `unshifted` scalar to hand them) had to be rebuilt to match ghostty's own `SurfaceView_AppKit.keyEvent` construction exactly; the client had been sending raw `NSEvent.characters` with control folded in, which is not what ghostty's own view does, and was silently wrong until an audit caught it (§6.6 below).
- **Frame diffing / grid extraction at the render boundary** — three iterators, a text arena, a wide-cell rule and a grapheme rule sit between `RenderState` and a drawable `Frame`, all hand-written and all outside anything ghostty's own parser can validate (see the conformance-testing discussion below — this is exactly where the risk concentrated).
- **The kitty-graphics unicode-placeholder scan** (`slopdesk-vterm/src/placeholder.rs`) — the engine stores virtual placements but reports no viewport position for them (the position is *encoded in cell colors and diacritics*), so decoding U+10EEEE placeholder runs during the frame fill is entirely hand-built, ported function-for-function from ghostty's own `graphics_unicode.zig` for the aspect-fit arithmetic specifically to avoid a sub-pixel seam between adjacent tiles of one image.
- **Sprite/tile rendering for box-drawing, block elements, Braille and Powerline glyphs** (`slopdesk-termrender/src/sprite/`) — deliberately *not* left to the font, because adjacent cells cannot agree on where ink stops if each glyph is fitted to its own font metrics independently; ported from ghostty's `src/font/sprite/draw/`.
- **The block/prompt model** (blocks, pinned command heads, docked prompt, the editor-like Warp-style prompt with its own undo stack, history, fuzzy-ranked ⌃R panel) — none of this exists in vt at all; it's product layer built entirely in `slopdesk-terminal`/`slopdesk-termrender`.

### Problems hit, verbatim

- **A silent iOS renderer UAF was inherited from the old fork and simply stopped existing** on deletion (upstream ghostty bug #13021, Metal-teardown use-after-free).
- **A soundness bug in the pinned bindings**: `ClipboardContent` built a `&str` with `from_utf8_unchecked` over an untrusted OSC-52 payload, and `ClipboardWrite::contents` sliced a null pointer on the "clear clipboard" shape — both reachable by any program on the pty, both caught by upstream's own Miri tests, fixed upstream (PR #81, closed issue #75) rather than patched locally.
- **The key-press shape bug** (§6.6, "ghostty parity pass"): the Mac view fed the engine raw `NSEvent.characters` with control folded in and no `unshifted` codepoint, silently diverging from ghostty's own construction; fixed by rebuilding the press exactly the way `SurfaceView_AppKit.keyEvent` does.
- **Draw redrew every display-link tick regardless of whether anything changed** — a shell sitting idle still paid a full Metal submit per cursor blink, and a program writing a byte a frame cost 120 full passes/sec. Fixed by making `draw` answer a status (nowhere/drawn/skipped/held) gated on the engine's own dirty flag plus a `repaint` bit set only by doors that change drawn state.
- **DEC 2026 synchronized-output mode was silently ignored** — the surface painted every intermediate frame of a synced update instead of holding until close, with a 1-second ghostty-matching timeout as an escape hatch for a program that opens sync and never closes it.
- **Font metrics rounded differently from ghostty's** in cell width/height/baseline/underline thickness — had to be re-derived to match `src/font/Metrics.zig` bit-for-bit, including an "odd line-height gain rule."
- **A block cursor on a wide (CJK) glyph only covered one cell** instead of both, diverging from ghostty's `cursor_wide`.
- **Bold brightened the color** (`SGR 1;31` rendered as bright red instead of dark red) because a pre-resolved color had already lost the information needed to apply ghostty's rule that `bold-color` is unset by default.
- **The Metal instance buffer drew its allocated *capacity*, not the frame's actual instance *count***, so a small frame following a large one redrew stale glyph/cursor/selection quads from the previous large frame — invisible because the tail bytes happened to be zeroed, until a specific repaint sequence surfaced it.
- **The wheel event was sent as a raw motion+button-4, not row-quantized presses**, so a program under mouse tracking got a motion report instead of the button-4/5 *press-per-row* ghostty sends, and a full-screen program under alternate-scroll mode (DEC 1007, on by default) got nothing at all — `less`/`man` didn't scroll under the wheel.
- **Chrome/gutter drawing was translated twice in one path and not at all in another** (a coordinate-transform bug pinned by two separate tests, "the same mistake in opposite directions").

### Verdict vs. alacritty_terminal / wezterm-term / vte

Not directly comparative in these terms — the decision predates the alternatives explicitly framed against libghostty-vt in this doc set, and the actual reasoning that survives is: **the core follows ghostty; the app layer is ours.** For anything underdetermined by spec (kitty-graphics aspect-fit arithmetic, sixel/iTerm2 refusal, sprite-glyph rules), the ruling is to take ghostty's own answer rather than derive one, "because the programs on the far end of the pty were tested against it and because its author has spent longer in this problem than we will." Sixel and iTerm2 image protocols were explicitly ruled **non-goals, not gaps** — ghostty `main` doesn't support them either, and adding either would mean a decoder maintained alone with no shared code path. The kitty "Glyph Protocol" (APC `_ 25a1`) is a **refused-but-owed** gap: the bindings expose the protocol's *setter* with no *reader*, so the engine claims support and then draws tofu; it's turned off at construction (`refuse_glyph_protocol`) until the bindings expose the glossary.

### Conformance testing — the thing that made trusting a hand-rolled render path safe

Since the engine's parser is upstream's (so VT *conformance* per se can't regress), the actual risk is entirely in the ~3 iterators + text arena + wide-cell/grapheme rules that sit between `RenderState` and a drawable `Frame` — all of it slop-desk's own code, none of it exercised by ghostty's own tests. Two complementary harnesses were built:

1. **Static double-reader oracle** (`slopdesk-vterm::conformance`): feed the same terminal to `RenderState` (the render path) and `Formatter` (an independent reader over `Screen`) and diff. Run over ghostty's own **fuzzer-minimized corpus** (`test/fuzz-libghostty/corpus/stream-cmin`, 3,271 files reduced from millions of fuzzer executions), which ships inside the vendored ghostty source tree at no extra cost. Break-tested: a deliberately injected 1-row shift failed 238/3271 inputs; a 40px paint offset failed 587/3271; a NaN glyph x failed 6040/3271 (some inputs trigger multiple check classes). Both sweeps combined run in ~6.5s parallelized across cores.
2. **Incremental-vs-fresh dynamic sweep** (catches the class of bug the static oracle structurally cannot: dirty-tracking bugs that only manifest across *multiple* frames). Feed a terminal the same bytes either in one shot or split across the exact chunk boundaries a real program produced (five real programs recorded via `slopdesk-ttyrec` — an OpenTUI/opencode demo, nvim, fzf, lazygit, `less`; 461 total `read(2)` chunks), then assert the two end states are byte-identical in content (not in bookkeeping like `revision` or dirty flags, which are supposed to differ). This is what caught the *actual production bug*: `VtSession::render` returned early on a clean-grid report and read cursor position/visibility *after* the early return — but the engine's "dirty" bit is about *cells*, and `?25l`/`?25h`/cursor-move-alone don't touch cells, so a program that only moved its cursor was silently misreported as unchanged. Symptom: a shell whose full-screen program exits and does a bare `?25h` shows no cursor at an idle prompt until the user types.

Break-test table proving the incremental-vs-fresh sweep's necessity: every one of {clean-flag bug, seam byte-swallow bug, key-encoder mode desync, pointer-encoder mode desync, cell↔pixel drift, bracketed-paste-always-off, focus-report-never-armed, resize-never-reaching-engine, the actual cursor bug} **passes the static oracle and fails the dynamic sweep** — the static oracle literally cannot see any of them, since it never looks at input encoding or a second frame.

## 2. Rendering: glyph atlas, Metal instancing, dirty tracking

- **Font metrics are copied from ghostty bit-for-bit** (`src/font/Metrics.zig`): cell width, natural height, cell height, baseline, underline thickness, including an "odd line-height gain rule" — with one deliberate divergence: cursor thickness keeps a `max(thickness + 1, 2)` floor because a 1px caret at 1× scale reads as a UI defect even though ghostty doesn't floor it.
- **Glyph atlas**: `AtlasFormat::Alpha8`, shared by text *and* sprites (box-drawing/Braille/Powerline) in one cache keyed by a private `CacheKey` enum rather than two maps, so atlas-growth invalidation logic exists exactly once. The atlas previously **refused every glyph past a 4096² ceiling forever** (returned cached `None` permanently) — fixed to reset-and-repack at the ceiling instead.
- **Metal instancing**: one instance buffer, doubles on growth and never shrinks; the shipped bug was that a draw call submitted the buffer's *capacity* rather than the *count actually written this frame*, so a small frame after a large one redrew the large frame's stale tail (a deselected paragraph's fill, a hidden cursor block). Fixed by making `fill` answer `Bound { buffer, count }` explicitly.
- **A dominant fast path for ASCII shaping** (`shape_monospace`, a single `CTFontGetGlyphsForCharacters` call over a run reading only the cmap, ~6× faster than shaping through `CTLine`) — but this is *unsound* for any font whose ligature/feature tables (`GSUB`/`GPOS`) substitute over plain ASCII, since cmap lookups skip substitution entirely. Fixed with a one-time-per-font-stack probe (`substitutes_over_ascii`): shape every ordered pair of printable ASCII through `CTLine` once at stack-build time (measured: 1.46ms for Menlo, 2.77ms for Helvetica, paid once not per frame — Core Text silently stops applying substitution on lines beyond ~10-12k characters, so the probe corpus is chunked to 2048 chars with 1-char overlap), compare against the cmap answer, and gate the fast path per font on whether it agreed.
- **Dirty tracking / draw skip**: the engine's own `RenderState::dirty()` and per-row `dirty()` bits are the whole mechanism — no separate dirty-rect system was built. A `draw` call answers a 4-state status (nowhere-to-draw / drawn / skipped / held-by-sync), and skip fires when the grid is `Clean`, the graphics generation matches the last-drawn one, and no UI-only state (scroll, selection, hover, focus, blink phase, theme, font, geometry, block collapse, marked text) has moved since.
- **Cursor blink**: a 600ms phase driven inside the display-link tick (matching ghostty's `cursor-blink` cadence), gated on whether the *last drawn frame* has a blinking cursor (cached per drawn frame, not re-evaluated per tick, since a frame that didn't change can't change the answer); reset to visible on every keystroke. One deliberate divergence from ghostty: `SGR 5` (blink attribute) text blinks on this same clock here, where ghostty draws it steady.
- **Underlines/overlines were drawn *over* the glyph** and had to move to a pass *under* the text so descenders cross the underline instead of being visually cut by it; strikethrough stays above. Underline color resolution (SGR 8 conceal, inverse, faint) had to be redone against *raw* style bits — a pre-resolved color has already lost the information those rules need.
- **Frame budget context**: encode-wall (VideoToolbox HEVC, unrelated to text rendering but the same machine/measurement discipline) measured 11–13ms typical with spikes to 15–19ms at 1280×800; the terminal's own painter quad-rebuild for a full-screen TUI measured 0.5ms/frame — considered under the "no measured regression" veto and left alone rather than optimized, since draw-skip already removes the whole pass on idle ticks (the common case).
- **Kitty-graphics z-ordering**: three z-bands interleaved into one draw pass (`images → backgrounds → images → glyphs → images → overlays`), one instance array visited three times via `baseInstance` rather than three separate arrays, so cursor/selection always draw last over any image.

## 3. Remote desktop pipeline

### Capture (ScreenCaptureKit)

Verified config (`docs/11-absolute-latency.md` §"Capture"), each item load-bearing:

| Setting | Value | Why |
|---|---|---|
| `SCContentFilter(desktopIndependentWindow:)` | single window | only public single-window capture path; `CGDisplayStream`/`CGWindowListCreateImage` obsoleted in macOS 15 SDK |
| `config.minimumFrameInterval` | `CMTimeMake(1, targetFPS)`, explicit | **macOS 15+ silently defaults to 1/60**, capping even a ProMotion display at 60fps if unset. Use `(1/fps) × 0.9`, **not** `kCMTimeZero` (refuted community claim) |
| `config.queueDepth` | 2–3 for LAN | Real SDK default is **8**, not the commonly-cited "3, range 3-8" — production configs run 1–2; IOSurface release deadline = `minimumFrameInterval × (queueDepth − 1)` |
| `config.pixelFormat` | `'420v'` (`kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange`) | feeds the HW encoder with zero color-conversion; BGRA forces a GPU blit (~0.5–2ms @4K) |
| `config.showsCursor` | `false` | client draws its own cursor, decoupled from video latency (see below) |
| `config.captureResolution` | `.nominal` | point resolution — 4× pixel reduction on 4K Retina |
| `config.ignoreShadowsSingleWindow` | `true` | strips the composited shadow, smaller bounding box |

`SCStreamFrameInfoStatus` is read first in the delivery callback; only `Complete`/`Started` are processed, everything else (`Idle`/`Blank`/`Suspended`) returns immediately to avoid idle-callback backlog. `SCStreamFrameInfoDisplayTime` shares a clock domain with `CACurrentMediaTime()` (both `mach_absolute_time`), refuting a "cross-domain" claim in older docs.

### Encode (VideoToolbox HEVC low-latency)

Exact property set, verified against SDK headers rather than transcribed as literals (this mattered — see §9 below for the literal-string bug it caught):

- `EnableLowLatencyRateControl = true` (in `encoderSpecification`, set at session creation) — **works with HEVC on Apple Silicon**, refuting Apple's WWDC21 "H.264 only" claim (FFmpeg's `videotoolboxenc.c` gates it `TARGET_CPU_ARM64 && codec == HEVC`).
- `RequireHardwareAcceleratedVideoEncoder = true`
- `RealTime = true`
- `AllowFrameReordering = false` (no B-frames)
- `AllowOpenGOP = false` — **HEVC defaults this to `true`**, must be explicitly disabled or IDRs aren't independently decodable
- `MaxFrameDelayCount = 0` — default is `kVTUnlimitedFrameDelayCount = -1`, **not** 0; setting 0 forces synchronous one-in-one-out emission
- `PrioritizeEncodingSpeedOverQuality = true`
- `MaxKeyFrameInterval = INT_MAX` (infinite GOP, on-demand IDR only via `ForceKeyFrame`)
- `ExpectedFrameRate` = target fps; `MaximumRealTimeFrameRate = 120`
- Rate control: `AverageBitRate` + `DataRateLimits = [bytes, seconds]`; **never** `ConstantBitRate` (mutually exclusive with low-latency mode, throws `kVTPropertyNotSupportedErr`); `MaxAllowedFrameQP = 36–40` caps per-frame size
- LTR (Long-Term Reference) recovery instead of periodic IDR: `EnableLTR = true` (codec-agnostic, confirmed usable with HEVC on Apple Silicon), `ForceLTRRefresh` (header self-contradicts type — annotation says `CFNumberRef`, abstract says `kCFBooleanTrue` — **test both `@(1)` and `kCFBooleanTrue` at runtime**), `AcknowledgedLTRTokens` (CFArray of CFNumberRef, client feeds back which LTR frames it received)
- `VTCompressionSessionPrepareToEncodeFrames` called once after setting properties, before frame 1, to eliminate the first-frame allocation spike

**The property-key literal-string bug** (`docs/57-apple-frameworks-in-rust.md`, the "vt row" ledger entry): `kVTEncodeFrameOptionKey_ForceKeyFrame`'s actual wire string is `"EncoderForceKeyframe"` — every *other* key in the surface (~20 of them) is spelled exactly like the tail of its own constant name, so a naive transcription would have looked correct to any reviewer, applied without error, encoded successfully, and **quietly shipped every forced IDR as a delta frame** — no recovery keyframe ever, nothing reporting a fault. Caught only by reading every key from the framework's own `extern` statics rather than typing string literals. `kVTQPModulationLevel_Disable` is `0`, not `-1` as its name would suggest — same class of trap, less dangerous.

**LTR as primary loss-recovery mechanism** (`docs/10-latency-optimization.md`): naive keyframe-on-loss recovery is actively counterproductive — a keyframe is 5–20× the size of a P-frame, so on an already-congested link the recovery keyframe adds queuing delay and *new* loss, making things worse. LTR-P frames (predicted from an acknowledged reference the client already has) are 10–30× smaller than a full IDR. Client acks received frames; host reports back which LTR tokens were acknowledged; on loss, `ForceLTRRefresh` asks for a small predicted-from-acked-LTR frame; falls back to a full keyframe only when no acked LTR remains at all.

### Packetize / FEC / MTU

- MTU: **1200 bytes** target datagram size (under the runtime MTU including WireGuard-mesh overhead). Data payload cap **1177 bytes** (`MAX_PAYLOAD_SIZE` = 1200 − 19-byte header − 4-byte length prefix). A parity shard is sized to its group's widest length-prefixed member.
- Datagram header carries: `streamSeq` (per-datagram, incremented in packetize order — data then parity — which is *not* send order once interleaving is on), `fragCount` (total fragments including parity), and a `flags` byte: bit0 keyframe/IDR, bit1 parity/FEC, bit2 "crisp" (an on-demand all-intra Session-B encoder), bits3-5 3-bit loss-adaptive FEC tier, bit6 isLTR, bit7 ackedAnchored.
- **FEC scheme**: XOR parity by default (`XORParityFEC`, `groupSize = 5` ⇒ ~20% redundancy, matching the Sunshine/Moonlight target) — one parity fragment per group of up to 5 data fragments, byte-XOR, zero-padded to the group's widest member length; recovers exactly one missing fragment per group. A `FECScheme` trait/protocol allows a **Reed-Solomon codec over GF(2⁸)** (NEON-accelerated, `slopdesk-gfsimd`) with an `AdaptiveFECPolicy` that scales redundancy % to measured link conditions — `m=1` is wire-identical to the XOR scheme, `m≥2` recovers multi-packet loss per group. Clean wired LAN target: 0–10% FEC + LTR + speculative loss detection; lossy Wi-Fi: 15–20%, multi-block splitting for large frames (Moonlight's own reference splits large frames into ≤4 independently-recoverable blocks; 4K uses lower FEC, ~5%, since frame size is already large).
- **Speculative loss detection**: predict a frame is unrecoverable *before* the next frame arrives (once shard counts prove it mathematically impossible) and fire loss-notify immediately rather than waiting — saves a full frame-time, self-corrects if wrong.
- **FEC-first with a NACK backstop** (re-scoped 2026-06-18, feature-flagged `SLOPDESK_NACK`, default off): FEC recovers at zero added latency; an unrecoverable frame is held briefly and the client NACKs the missing fragments, which the host re-sends from a ring — the old "never retransmit" rule assumed naive replay-and-stall, but with a playout buffer much larger than RTT, a retransmit lands *inside* the buffer with no visible stutter. LTR-refresh/IDR remains the fallback once the retransmit grace period expires.
- **A real production bug**: parity datagrams were computed at 1204 bytes, 4 bytes over the actual budget — fixed by deriving `MAX_PAYLOAD_SIZE` correctly (datagram size − header − length-prefix), with the packetizer's own tests now bounding every emitted datagram by `MAX_DATAGRAM_SIZE` and the reassembler capping accepted parity fragments at exactly that size.

### Transport: why UDP over QUIC/TCP

Plain UDP + custom FEC/congestion control, not QUIC, not TCP. Reasoning (`docs/13-network-transport.md`): the deployment model assumes a **trusted private WireGuard mesh** (NetBird/Tailscale-style userspace WG) providing E2E encryption and node auth already, so a second crypto layer (QUIC-crypto or TLS) is pure redundant overhead with no security benefit — "the security boundary is the network, not the app." A userspace WG interface (`utun*`) reports as `.other` to `Network.framework`, so `requiredInterfaceType` pinning (e.g. `.wiredEthernet`) actively **breaks** the mesh case and must be left unset. WireGuard also **zeroes the outer DSCP** field (only ECN survives the tunnel), so `serviceClass = .interactiveVideo` QoS marking is a no-op through the tunnel — congestion control and adaptive bitrate must be handled entirely in the application layer instead (`LiveCongestionController`/`LiveBitratePolicy`, a delay-gradient + loss-driven controller rather than naive min/max ABR bouncing). This is a **corrected ruling** — the doc explicitly lists three earlier assumptions in `03-transport-protocol.md` (`requiredInterfaceType` pin, `serviceClass` as "most important lever", QUIC datagrams for TLS+CC) as superseded once the mesh model was taken seriously.

### Client decode / present

- Decode: `VTDecompressionSessionDecodeFrame(flags: 0)` — synchronous, no reorder buffer; **never** set `kVTDecodeFrame_EnableTemporalProcessing` (licenses display-order callback delays). `RequireHardwareAcceleratedVideoDecoder = true`. Measured decode wall (HEVC, 1280×800, real audit): delta p50 0.70ms / p90 0.87–1.0ms / max 1.3ms; **cold IDR after session create: 105ms**; warm IDR: 2.7–5.0ms.
- Render: `CAMetalLayer` + `CVMetalTextureCache`, explicitly **not** `AVSampleBufferDisplayLayer` (measured/documented to add ≥1 frame of buffering). `maximumDrawableCount = 2` (refuting a community claim that this is "not recommended on iOS" — the only real constraint is the value must be 2 or 3). Zero-copy: `CVMetalTextureCacheCreateTextureFromImage` twice per biplanar frame (once per plane), same IOSurface the decoder wrote, no GPU copy on Apple Silicon's unified memory.
- **Present-queue policy** (`slopdesk-video/src/present_queue.rs`): homeostatic depth — trims to the live delivery depth on every present rather than holding a fixed cap, with a 2-slot re-prime floor, and refresh ticks are counted in *content slots* so a 120Hz display link doesn't misread the gaps between 60fps content arrivals as starvation. A real bug: the queue previously **ratcheted to its hard cap under sustained motion** and never came back down.
- **Vsync finding, measured directly** (`docs/71-video-smoothness-2026-09.md`): vsync-locked present costs **+6ms at p50 under 30fps** (clean, metronomic: exactly 60.0 new-frames/sec) but **+29ms at p50 once the pipeline runs at the 60fps default** — glass-to-glass p50 21.2ms / p90 28.2ms **unlocked** vs. p50 50.5ms / p90 52.8ms **locked**, a genuine two-frame cost once content rate roughly matches refresh (both drawables fill, every frame waits out a queue). **Default ships with vsync OFF**; the renderer's own code comment claiming "Parsec presents without vsync by default" was checked against Parsec's actual published docs and found wrong — Parsec's `client_vsync` defaults ON and pays the same tax.
- A separate present-queue bug: **a second arrival within one vsync interval, under a locked present, pushed the first frame out** before it ever displayed — fixed by marking `needsRedisplay` and returning rather than swapping immediately (gated to `SLOPDESK_VSYNC=1` on macOS, always-on for iOS).
- **Encode-load pacer trap** (also `docs/71`): a rate-halving pacer (60fps→30fps) tripped whenever the measured encode-wall EWMA exceeded 85% of the frame budget for 3 consecutive frames, then took 45 clean frames to step back up. At 1280×800 the actual encode wall is 11–13ms with spikes to 15–19ms — 72% of a 16.7ms/60fps budget — so ordinary spikes tripped the pacer constantly (measured: 45–133 host-side send-gaps per 15s span, delivered fps dropped to 49–54). Recalibrated to step down only when the *average* exceeds budget, for 30 consecutive over-budget frames (half a second), and step back up after 120 clean frames — after the fix: 0 pacer steps, 1–3 send gaps, 59.0–59.4 new frames/sec (i.e., the source's own cadence, not a ceiling the pipe adds).

### Cursor channel

Sent as a **separate low-latency channel from the video stream itself**, not composited into the encoded frames — `showsCursor = false` at capture, client draws a local Metal overlay fed from the position channel, so cursor feedback latency is **RTT (~2–5ms measured) instead of the full video pipeline latency (~15–25ms)** — described as the single highest-value, most commonly missed win, matching what RDP/PCoIP/NoMachine all do. Position updates are deduplicated with a 1Hz keepalive; shape refresh is seed-driven (fires only on an actual shape change) rather than continuous TIFF re-encoding — a fixed production bug had the cursor channel sending 120 datagrams/sec even while completely idle.

### Input injection

`CGEventPostToPid` (delivers directly to the target PID, no system cursor move, no window-raise side effect) — **not** a pure Mach IPC round-trip as commonly assumed; it's a multi-hop CoreGraphics→WindowServer call whose Apple Silicon latency has never been independently benchmarked. "Activate-then-control" uses the private `SLPSPostEventRecordTo` (SkyLight) called twice, to activate a window without raising it (avoids a 100–300ms Space-switch side effect). On macOS 26, an **unsigned daemon's `CGEventPost` for modifier+key combinations is silently dropped** — the documented workaround requires code signing or a DriverKit virtual HID client. Key-repeat state and scroll modifiers ride the wire as explicit bits (a state byte with bit0=down/bit1=autorepeat for keys; a trailing modifiers byte for scroll events) — an early bug had both missing entirely, so a held ⌘ during a scroll gesture from a client that hadn't separately sent a ⌘ keydown wouldn't zoom on the host.

### Measured glass-to-glass latency vs. Parsec

| Configuration | p50 | p90 |
|---|---:|---:|
| Loopback, 60fps default, vsync off (30 pairs) | **21.2ms** | 28.2ms |
| Same, `SLOPDESK_VSYNC=1` | 50.5ms | 52.8ms |

Judged against a documented envelope of 52.8–60.2fps continuous-scroll fidelity from earlier profiling; the doc is explicit that this was measured **loopback on one Mac Studio only** — the WireGuard-mesh case was never measured because the second test machine was unreachable that session. Parsec's own published number is 4–8ms @240fps wired, but explicitly scoped as *display-to-display only* (no input, no full glass-to-glass, extreme stress demo — Parsec itself recommends 60fps normally), so it's not a directly comparable figure; the slop-desk number above is closer to genuinely full-pipeline.

### Audio

Rides the same media socket as **channel 6** alongside video (2026-07-17 decision), not a separate connection.

## 4. PTY/terminal transport

### Why a separate supervisor (`slopdesk-superd`) holds PTY masters

The core problem: hostd (the daemon that owns the mux, replay buffer, screen model, everything latency-sensitive) needs to be freely rebuildable and restartable during development *without killing the user's running shells*. If hostd itself held the PTY master fd, hostd exiting would drop the fd's refcount to zero and every child shell would get `SIGHUP`. So a small, boring, rarely-changed daemon (`superd`, a macOS LaunchAgent, `RunAtLoad` + `KeepAlive`) forks every pane's shell via `openpty` + `fork` + `execve`, keeps its own duplicate of the master fd open for the pane's entire life, and hostd merely holds a *second* duplicate. **If hostd crashes** (the common case during development), nothing is lost — the next hostd asks superd for the pane list and re-adopts by fd; superd is what actually owns `TIOCSWINSZ` and the load-bearing `tcgetpgrp()` syscall (the foreground-process-group read agent-detection depends on). **If superd crashes**, the panes genuinely are lost — fd custody dies with the custodian, and launchd relaunching it cannot reconstruct the fds. superd is intentionally tiny and dependency-free specifically to make this failure mode rare.

superd also **binds** the two long-lived Unix-domain sockets Claude Code hooks and `ctl` connect to (`slopdesk-agent.sock`, `slopdesk-ctl.sock`) at boot, and hands the *accepted connection* — not a relayed byte stream — to whichever hostd currently claims it, over a superd-owned control protocol. This is explicitly **not a protocol relay**: superd never touches the bytes of either socket's application protocol, it only does the OS-level accept-and-forward-the-fd step, so a hostd restart doesn't drop a hook connection Claude Code has already opened.

The protocol between superd and hostd is deliberately kept minimal (spawn, list, signal, exited, socket forwarding) because **changing it costs a superd restart, which costs every live pane** — superd outlives hostd's build cycle by design, so the wire compatibility discipline is: a `hello` on both sides carries a version, superd serves any hostd whose *major* version matches, and a `buildVersion` field on the hello reply lets hostd detect drift and *report* it (never auto-restart superd, since that would kill every pane — left as the user's call).

### Ring buffer / scrollback replay

Two genuinely distinct ring/replay mechanisms exist at two different layers:

1. **superd's per-pane `OutputRing`** (`rust/slopdesk-superd/src/pump.rs`) — a dedicated `poll(2)` thread per pane reads raw PTY bytes and stores them at **absolute offsets since the pane was born**, bounded by `SLOPDESK_PANE_RING_BYTES` (**4 MiB** default), evicting oldest past that. On a pane's reaper cleanup (exit), the ring is moved into a bounded **graveyard of 16 panes** rather than freed immediately, so a fast-exiting command's final output can still be read for a race window. This exists specifically because superd, not hostd, now does the actual `read()` off the master (reversing an earlier design where superd held the fd but never read it) — without *someone* draining the master continuously, the kernel's own PTY buffer fills and blocks the child process the moment hostd is mid-restart.
2. **hostd's `ReplayBuffer`** (`rust/slopdesk-wire::replay::ReplayBuffer`) — the wire-level seq-numbered scrollback ring used for client reconnect/replay, distinct from superd's raw byte ring. Carries the seq ledger, line-aligned eviction, an alt-screen "cut repair" (`altscreen::reopen_sequence`, for a scrollback eviction that beheads an in-progress DECSET-opened alternate-screen segment), a byte-distiller re-chunker, and an O(log n) lag metric. Never drops unacknowledged data — backpressures by pausing the PTY drain instead of evicting.

### Multi-client fan-out

A single PTY session can have **N attached viewers** (`docs/45-multi-client-state-sync.md` §8). Each subscriber gets its **own** `ReplayBuffer` read cursor; joining triggers the same `SnapshotReplayPolicy`/`composeSnapshotReplay` state-transfer path used for an ordinary cold reattach (renders the current `TerminalScreenModel` once rather than replaying full byte history — this is what makes multi-attach affordable at all: "eviction costs one screen, not a history"). Retention across N subscribers releases at `min(lastAckedSeq)` across all of them (a genuine min-fold over the whole subscriber set, not a single watermark). A subscriber more than **`SLOPDESK_SUB_LAG_BYTES` (default 32 MiB)** behind the fastest is **evicted** (`channelClose` with reason `subscriberEvicted`) rather than allowed to stall the whole pane for everyone else — deliberately set *below* the separate 64 MiB `ReplayBuffer.offlineGateBytes` pause-the-PTY-drain threshold (itself capped at a 256 MiB hard ceiling), so eviction fires before the PTY drain would ever need to pause. The PTY drain only pauses once the *last* subscriber is gone. Fan-out width is bounded by a `u8` child count (≤255) checked before allocation. Close (`closePane`) is explicitly **not refcounted** — it always tears down the shell and notifies every subscriber via `channelClose`, distinct from a mere subscriber-count-hits-zero detach (which parks the session for later reattach).

### Credit-based flow control

The mux-level channel handshake (`docs/20-wire-protocol.md` §8.3.1) sends `channelOpenAck` with an explicit `resumeFromSeq` (0 = fresh shell, resets marks; >0 = same live session reattached, keeps marks) **on the DATA link before any `output` frame**, specifically so a restored scrollback transcript can never race ahead of the verdict that tells the client how to interpret it. Video-side credit windows and ack cadence: the client→host telemetry window (`networkStats`, message type 5) rides roughly every **50ms** and carries 11 `UInt32` fields — `framesReceived`, `fecRecovered`, `unrecovered`, `latestHostSendTs`, `clientHoldMs`, `owdJitterMicros`, `owdTrendMilli`, `owdTrendFlags`, `pacerLateFrames`, `pacerPresentGaps`, `pacerDepth` — every field deliberately **relative** (windowed counters, host-timestamp echo, client-local deltas) so the host can derive RTT in its own clock without any clock-skew assumption between machines.

### The pre-ack wedge bug

The load-bearing bug of this whole layer, and the reason for an explicit rule in the wire-protocol doc:

> **Rule: `output` that reaches the client ahead of the ack's adoption is STAGED, not folded.**

The concrete failure: the frame decoder that reads `channelOpenAck` off the socket does not itself block waiting for the connection-level state machine to *adopt* that ack before continuing to decode the next frame on the same socket — so an `output` frame sitting immediately behind the ack in the byte stream can be decoded and handed to the session-fold logic *before* the ack's `resumeFromSeq` verdict has been applied. If that happens, the output gets folded against the **previous** connection's stale seq marks and credit accounting, gets "credited to no transport," and has its credit zeroed by the reset the (not-yet-applied) ack was about to bring. Concretely: **a restore the size of one credit window (64 KiB) wedges the pane** — the pane's flow-control state gets stuck believing it has no outstanding credit, and nothing ever unsticks it. The fix (`slopdesk-clientdriver`) is to hold any `output` frame that arrives before the client's own connect logic has adopted the ack, and feed the held frames back through, in order, once adoption has happened. Measured before/after: reproduced **15 wedged / 20 runs** before the fix; **0/20** after, pinned permanently by `tests/preack.rs`. This exact class of bug (a verdict racing behind data that depends on it, on the same ordered byte stream) is presented as a general lesson, not a one-off — "the discriminator byte lets the host route a freshly accepted connection without parsing a frame" is the same discipline applied one layer up in the preamble design (§8.1) specifically to avoid needing this kind of staging at connection-establishment time; it only remained necessary at the ack/resume boundary because the ack itself is *inside* the frame stream rather than a preamble.

Other real bugs in this area worth carrying forward as class-level lessons: `tcgetattr` was called **per input message** instead of once per scheduler quantum (fixed — a paste or key-repeat burst now samples once per gap, not once per byte); a subscribe/attach path delivered one output chunk **twice** (fixed by cutting the overlap by absolute offset, mark only ever moves forward, never re-emits); superd's ring was walked **a byte at a time under its lock on every subscribe** (two full `memcpy`s fixed it).

## 5. Claude Code integration

### Hooks and detection architecture

The full picture (`docs/50-agent-detection-architecture.md`) is a **two-tier fusion state machine**, one instance per pane, rebuilt from a 2026-08-11 postmortem after a real user-visible bug (Tab-switching an `AskUserQuestion` dialog flapped the pane's status between blocked and idle on every keypress).

**Tier 1 — the agent describing itself, authoritative.** Sources: Claude Code's own hook events delivered over an `AF_UNIX` socket (`AgentHookListener`); a `slopdesk ctl report working|blocked|done|idle` verb any process in any pane can call (deliberately name-agnostic — a codex/gemini/opencode wrapper that calls `ctl report` gets identical first-class treatment with zero per-agent code); foreground-process-*absence* (~1Hz poll); a cancel keystroke sent raw into the PTY. **While tier 1 is live, tier 2 may corroborate but never overrule.** Coverage is per-*session* (a fresh `claude` process in the same pane earns its own coverage on its own first hook) and is **not a recency window** — a question sitting unanswered on screen for ten minutes is silence-by-design, not evidence the feed died; timing that out would reintroduce the exact bug this architecture exists to fix, just at a 10-minute period instead of a fraction-of-a-second one.

**Tier 2 — inference from pixels**, corroboration only: a herdr-derived screen-rule ladder (regex/heuristic matching against the rendered grid, differentially verified against upstream herdr's own manifest set); OSC 0/2 title text (trusted more than the rule ladder specifically because it's *also* the agent's own emission — Claude Code writes a Braille spinner glyph while working, `✳` at rest); raw process-presence; a legacy coarse manifest verdict.

**The dissent watchdog** is the escape hatch when hooks are unreliable (relay dies, host restarts mid-session, a record is lost): a stopwatch tracks how long the screen has *continuously* disagreed with the authoritative tier-1 status, reset to zero by any single agreeing read. Two asymmetric windows — 3 seconds to let the screen **raise** a block (an unannounced dialog blocking a human is the expensive failure to miss), 10 seconds to let the screen **release** one or contradict `working` (releasing early both flaps the UI and mints a false "turn finished" notification). Past the window, coverage drops and the screen verdict applies, tagged as a `quiet` transition (raises no user-visible attention — banner, sound, badge — it's the detector correcting itself). Critically: **nothing legitimate ever needs to wait on this window** — every real way out of a block (question answered, permission approved/denied, a call failing, an MCP elicitation answered, the turn ending, an Esc-cancel) has its own instant tier-1 signal.

**The block ledger** is a *set* of outstanding tool calls keyed by `tool_use_id`, not a boolean flag — because Claude Code emits tool calls in batches, so "a tool finished" and "the human answered" are not the same fact once a turn fires `[AskUserQuestion, Bash]` together; the `Bash` result must not clear the block the still-unanswered question opened.

**Session ownership**: a pane belongs to exactly one Claude Code session id at a time, keyed off the hook envelope's `session_id` (not any tool-call field, since some hook shapes carry none). A nested `claude -p` spawned by the owning agent's own Bash tool call inherits the same `SLOPDESK_PANE_ID` env var and would otherwise post its full hook set *to the parent's pane* — its `SessionStart` would clear the real agent's block, its `Stop` would mint a false "finished" notification, all while the real agent still sits blocked on a human. Fixed by claiming ownership on first id-carrying event and dropping (not misapplying) any event naming a different session — with one deliberate exception for crash recovery: a `SessionStart` from a different session is allowed to take over *only* when the pane's current status is already at rest (idle/done/none), since a nested run can only ever be spawned while its parent is `working` or blocked, by construction, so "the pane is at rest" cleanly discriminates a crash-restart from a nested run.

### Documented weaknesses

- **Race between a shell printing its own prompt (PTY bytes) and the host reporting a block record (control message)** — the two don't order against each other, so there's a window where the frame shows one more prompt than the host's records account for. Handled with a guess-then-verify scheme (try anchor offset 0, then 1) that is deliberately one-sided: an unmatched guess proves nothing, only a *contradiction* fails, and a frame that can't be verified against known command text prints nothing rather than a guessed wrong exit code.
- **A hook does not reset the dissent stopwatch** — an earlier version cleared dissent on every hook, which meant the watchdog could never mature *while a turn was still emitting hooks*, which is precisely when a stale block would need correcting.
- **Screen-rule "region" scoping is a real, documented divergence from upstream herdr** — herdr has no concept of a gate reading a *different* region than its parent rule, which made one whole rule (`live_prompt_box`, five footer-text needles) dead code: a modal dialog's footer sits below the last horizontal rule, structurally outside the region the rule's own body-matcher was scoped to, so the veto never saw the thing it was written to catch, while the dialog's focused-option caret (`❯ 1. …`) satisfied the *positive* match — producing the strongest possible "idle" verdict for a pane that was actually blocked on a human. slop-desk added cross-region gate syntax to fix this class of bug.
- **A call can end without `PostToolUse` at all** — Claude Code emits `PostToolUseFailure` on the exception path instead, and a naive ledger (immune-to-other-calls-by-design for `.ask` entries) would leave a hand raised over a dialog that had already vanished.
- **An interrupt (Esc) is not a failed call, it's a finished turn with no `Stop` event at all** — mapping it as an ordinary tool failure pinned the pane `working` with a spinner up for the full 10-second watchdog window, then announced "turn finished" for a turn the user had actually cancelled.

## 6. Infinite canvas

**Status: fully designed, partially implemented, then explicitly retired** in favor of a conventional Session→Tab→n-ary-split-tree IDE layout (`docs/30-infinite-canvas.md` marked SUPERSEDED/HISTORICAL; see `DECISIONS.md` "Retire the infinite canvas"). Kept only as a design record.

Two hard physical constraints drove the whole design and remain relevant for Slopty even without a canvas: (1) a terminal surface sizes itself from its host view's `bounds × contentsScale` **in points**, and pins `layer.bounds == view.bounds` — so the camera had to be a **pure translate**, never a scale/`CGAffineTransform`, on any ancestor of a terminal view, because a scaled ancestor desyncs the 1:1 points-with-y-flip mouse-coordinate mapping the renderer assumes. (2) Terminal panes were **never culled** off-viewport (kept mounted, just translated off-screen), because unmounting closes the underlying surface, and remounting later replays only a capped retained-output ring — which can show a **stale frame for an alt-screen TUI** (vim, tmux) indefinitely on a static screen, since nothing forces a repaint. Video/remote-desktop panes *were* culled off-viewport (with a margin) to free a limited concurrent-video-session slot, since re-establishing a video connection has no stale-frame risk. Z-order was an **explicit integer field per item**, deliberately not array order, specifically so persistence/dedup/repair logic touching the item array could never accidentally reorder the visual stack. New-pane placement used an NSWindow-style cascade with collision-nudge, plus a store-level "guarantee visible" pass that pans the camera to include a newly created pane if placement left it off-screen. The whole model was a flat `{ items: [CanvasItem], camera: CanvasCamera }` value type — replacing an earlier recursive split-tree `PaneNode` enum specifically to drop a hand-written recursive `Codable` implementation in favor of a synthesized one.

The retirement reasoning (from `DECISIONS.md`, not itself pulled in full here) favored a conventional tiled-split IDE layout as more discoverable and more consistent with what users actually expect from a coding tool — worth knowing that this was tried, shipped, then deliberately walked back, rather than something Slopty should treat as settled product direction.

## 7. Apple frameworks from Rust

### The ruling and the crate family shape

Originally the invariant was "Rust core, Swift view+effects boundary" — all `CGEvent.post`, `SCStream`, `VTCompressionSession`, `AXUIElementPerformAction`, `IOPMAssertionCreate`-class calls stayed in Swift (~12-14k lines, concentrated in two daemons with no UI at all: `videohostd`, `hostd`). This was later reversed: **that effect layer moved to Rust too**, leaving Swift with only the actual view layer (AppKit/UIKit, SwiftUI) and the thin faces that call into Rust over FFI. This produced a family of ~20 small `slopdesk-apple-*` crates, one per framework *area* (not per framework — e.g. `NSCursor` and `NSEvent` got separate crates on the theory that "what the cursor looks like" and "where the input hardware is" are different questions one sampler happens to read).

### Crate choices and exact versions

`objc2` family, all pinned **exact** (`=`, not caret — the whole family shares a generated ABI surface and must move as one unit or not at all): `objc2` **0.6.4**, `block2` **0.6.2**, `dispatch2` **0.3.1**, and 19 separate `objc2-*` per-framework crates (screen-capture-kit, video-toolbox, core-media, core-video, io-surface, metal, core-graphics, app-kit, ui-kit, core-foundation, io-kit, etc.) all at **0.3.2**. Chosen over hand-declared `extern "C"` blocks for three concrete reasons: (1) a hand-declared signature's correctness depends on matching an SDK header nobody in the crate has actually read, an unauditable obligation; (2) Core Foundation/Objective-C retain-count correctness is encoded in the *type* via `CFRetained<T>`, turning a leak into a compile error; (3) measured, most of the actual API surface needed turns out to be safe Rust — e.g. `objc2-core-graphics`'s `CGEvent.rs` is 31 safe functions vs. 7 unsafe ones (the raw-pointer keyboard/tap-creation calls), and `CGEventSource.rs`/`CGRemoteOperation.rs` are 24 functions with **zero** unsafe — meaning the entire input-injection path (build event, set fields/flags, warp, post) is safe Rust end-to-end.

### The unsafe-admission discipline (worth copying verbatim as a design pattern)

Each `slopdesk-apple-*` crate is capped at roughly 600 lines of *code* (blank lines/comments/tests excluded — deliberately, since roughly half the code in these crates is `# Safety` prose), forbids hand-rolled `ptr::read`/`transmute`/`from_raw`/`slice::from_raw_parts` with **exactly one counted exception per crate**: `CFRetained::from_raw` (Copy/Create-rule, +1 retain via an out-parameter the binding can't type as owned) and `CFRetained::retain`/`Retained::retain` (Get-rule, a borrowed +0 reference needing to outlive a callback), each capped at one call site per crate and enforced by a static-analysis gate (`apple-family`) that fails if the count is wrong *in either direction* — including failing at **zero**, since an unused admission is a door nobody should have left open. Three crates (`apple-audio`, `apple-vt`, `apple-metal`) are named exceptions permitted broader raw-pointer use, specifically because their frameworks hand out *memory* (a `AudioBufferList` C flexible-array member, a locked `CVPixelBuffer` plane pointer, an `MTLBuffer`'s mapped `contents()`) rather than *objects* — there is structurally no `CFRetained`-shaped answer for those. Every `unsafe` block must name the *framework* rule it satisfies in its safety comment, not a Rust-level property the binding already proved.

### Concrete pitfalls found

- **A leak-test requirement exists specifically because generated bindings are "audited" only per-commit** — create-and-drop-in-a-loop, assert resident memory doesn't climb, for every crate's central object.
- **A `dlsym`/function-pointer resolution requirement for two private APIs**: `_AXUIElementGetWindow` (no public binding at all) and a private window-server cursor-seed symbol — both function-pointer transmutes, which the raw-pointer ban still forbids outright even for the exempted crates, so both were routed to a shared `posix::dynsym` helper. One real bug found here: two different frameworks were briefly resolved through one shared handle, and asking the wrong framework image for a symbol it doesn't export **answers null rather than erroring** — permanently dead, silently, until a test pinned the two-image split explicitly.
- **`NSWorkspace.frontmostApplication` is a per-process snapshot that freezes solid inside a daemon pumping no run loop** — a real bug fixed by moving to `CGWindow`-level queries instead, which don't depend on a run loop being alive.
- **A large VideoToolbox wrapper (`VideoEncoder.swift`, ~1500 lines) turned out to be roughly 350 lines of actual framework calls and ~1150 lines of pure decision logic (env parsing, clamps, a 7-field rate-control state machine) that had *never been unit tested* in Swift**, because the file's own header admitted `VTCompressionSessionCreate` hangs without a live window server and Screen Recording permission — so a constructor nobody could call in CI held rules nobody could test. The Rust port deliberately split this into three pieces (framework calls / pure decision rules / a thin join), which is what let 18+ new tests exist for logic that had literally never run under any test harness before. The same pattern repeated for the decoder, `AXUIElement` reads, and cursor sampling — described as "two-thirds decisions," where reading the port as "wrap the framework calls" undercounted the actual value by roughly 3×.
- **A genuine silent bug found only by porting**: a drop-relief counter only incremented inside one branch of an `if/else`, so under one rate-control mode it accumulated for the *entire process lifetime* and was never drained — in exactly the mode most likely to produce drops, the diagnostic number a person would read to investigate them was the one number that could never be trusted.
- **A `#[link(name = "VideoToolbox", kind = "framework")]` attribute does not survive `xcodebuild -create-xcframework`** — it lives in the Rust rlib's own metadata, but what ships out of the xcframework step is a plain static archive with none of that metadata attached. Every framework a Rust crate calls C functions from (as opposed to Objective-C classes, which resolve at runtime through the ObjC runtime and don't need this) has to be **separately, manually named in the Swift package's `linkerSettings`** — VideoToolbox and CoreMedia for C functions, CoreVideo for three `extern` `kCVImageBuffer*` color-space constants. Missing one presents as a wall of undefined symbols **at the final app link**, long after the Rust crate and its own CI gate are both green — described explicitly as a trap every future framework-wrapping crate will hit again.
- **An `extern` static symbol read from a generated binding (`SCStreamFrameInfoStatus`) has the identical linking trap** — it's a linker-resolved symbol (unlike a class lookup), so `ScreenCaptureKit` also has to be manually named in the Swift package.

### iOS specifics

VideoToolbox is the first crate in the family to actually reach iOS (everything before it was macOS-gated, since the underlying APIs mostly don't exist on the phone at all): the compression half is `#[cfg(target_os = "macos")]`-gated (only the host ever encodes), while the decompression half is left ungated and reachable from both platforms (every client decodes) — verified by a build-time gate that asserts the encoder's exported symbols are present on the macOS build slice and *absent* from both iOS slices, so a `#[cfg]` regression fails loudly at build time rather than merely bloating the phone binary. The decoder's callback hands the decoded `CVImageBufferRef` over at **+1 retain** — Swift's `takeRetainedValue()` performs the required release — the exact *opposite* ownership convention from the encoder's callback, which lends `(ptr, len)` only for the duration of the call and requires the *caller* to copy. This asymmetry is deliberate (the decoded buffer is handed to a display-link pacer that holds it well past the callback's return, so a borrow would be a first-frame use-after-free) but is explicitly called out as the kind of thing that must be *written down at the FFI boundary*, not left to be inferred from symmetry with the encoder.

Two crates (`apple-pasteboard`, `apple-text`/CoreText) are gated `any(macos, ios)` rather than `macos`-only, deliberately narrower than `target_vendor = "apple"` — the tree builds exactly three slices (macOS, iOS, iOS Simulator) and the wider vendor spelling would silently also claim tvOS/visionOS nobody actually compiles for.

No Xcode-project-structure or entitlements/code-signing detail beyond what's implied above (the framework-linking trap, and the macOS-26 requirement that `CGEventPost`-from-an-unsigned-process be either code-signed or routed through a DriverKit virtual HID) surfaced in the docs read for this report.

## 8. Dependency list (`rust/Cargo.toml` workspace + audited crate versions)

The top-level `rust/Cargo.toml` workspace itself only lists the *short-lived, forked-per-event* binaries (`slopdesk-hook`, `slopdesk-ctl`, `slopdesk-cli`, `slopdesk-probe`, `slopdesk-sidecars`, `slopdesk-hostlaunch`) as members — every daemon and library crate is deliberately its *own* separate workspace root (excluded from the parent, linked as a path dependency instead), specifically so each daemon can carry its own `[profile.release]` tuned for its own workload. The shared members' profile is tuned for **process-startup latency, not throughput** — the hooks fire twice per Claude Code tool call, `slopdesk` once per keystroke: `opt-level = "z"`, `lto = true`, `codegen-units = 1`, `panic = "abort"`, `strip = true`. Lint posture is maximal-strict: `unsafe_code = "forbid"` workspace-wide for this group, `clippy::{all,pedantic,nursery,cargo} = "deny"`, plus a curated slice of `restriction` lints — notably `unwrap_used`/`expect_used`/`panic`/`panic_in_result_fn` all `deny`, with the explicit rationale that a panic here is a non-zero exit that Claude Code surfaces as a broken turn.

**Audited crate + version list** (from `docs/69-dependency-currency.md`, taken 2026-09-02 — every one of these was, at that date, exactly at registry-latest, not merely within a caret range): `serde` 1.0.229, `serde_json` 1.0.151, `nix` 0.31.3, `libc` 0.2.189, `regex` 1.13.1, `base64` 0.23.1, `socket2` 0.6.5, `sha2` 0.11.0, `rayon` 1.12.0, `toml` 1.1.4, `unicode-segmentation` 1.13.3, `percent-encoding` 2.3.2, `zip` 8.6.0, `tar` 0.4.46, `flate2` 1.1.10, `libz-sys` 1.1.29, `xattr` 1.6.1, `ureq` 3.4.0, `png` 0.18.1, `rtrb` 0.4.0, `cpal` 0.18.2, `git2` 0.21.0, `sha1_smol` 1.0.1 — plus the exactly-pinned `objc2`/`block2`/`dispatch2`/`objc2-*` family described in §7.

**Deliberately absent dependencies** (a standing decision, not an oversight): no async runtime, no `anyhow`, no `tracing`, no `clap` (every CLI parses `std::env::args` by hand, since these binaries are forked per keystroke/per tool-call and the release profile above exists specifically to make process startup, not argument parsing, the cost worth optimizing).

**Reinvented wheels, each with a written reason for not using the obvious crate** (worth internalizing as a checklist, not copying the specific reasons blindly):
- A hand-written VT escape scanner runs beside `libghostty-vt` in the *replay-transform* path specifically because it operates on retained bytes **before any terminal engine exists to ask** — an engine can answer "what did these bytes do to a grid," never "what is structurally present in this byte stream with nothing attached."
- A hand-written JSON writer exists beside `serde_json` because byte-exact escaping against two specific on-disk persistence formats was **measured** to disagree with `serde_json` on three particular escape sequences, and the crate additionally needed to guarantee zero transitive dependencies to callers on the wire-decode hot path.
- A hand-written regex-adjacent scan crate exists specifically to let two *other* crates (`slopdesk-terminal`, `slopdesk-sanitize`) keep a genuine zero-dependency guarantee while still getting linear-time pattern matching against remote-controlled (i.e., adversarial) text.

## 9. What went wrong / explicit reversals and rejections

This project's docs use "rejected"/"re-scope"/"superseded" far more than "mistake," but the substance is the same — architectural bets tried and explicitly walked back:

- **CRDT/OT for shared state was evaluated and rejected** in favor of plain host-authoritative RPC broadcast, citing Zed's own real-world precedent that even Zed — a genuine CRDT product for text buffers — uses host-authoritative broadcast for its Project/Worktree tree, "the structurally identical case to ours," because with one serialization point (the host) there's nothing to actually merge.
- **An operation log with delta compaction was rejected** in favor of snapshot-at-current-state, specifically because compaction introduces an unbounded retention window and an `OffsetOutOfRange`-shaped failure mode that a stateless snapshot-and-diff approach simply doesn't have — cost becomes O(tree-size), never O(elapsed-time), so a 4-hour-stale reconnect is the *same code path* as steady-state sync.
- **WezTerm's/`screen -x`'s unconditional last-writer-wins for terminal resize was rejected** — two clients at different window sizes fight, and whichever raced second silently wins with no signal to the loser.
- **An input-keyed resize-driver latch was rejected** for having no hysteresis: two clients typing alternately would flap `TIOCSWINSZ` + `SIGWINCH` + a full TUI repaint on every single exchange.
- **A presence-heartbeat-keyed resize predicate was rejected** — a 30-second liveness heartbeat is not evidence a client actually wants to drive terminal size; ordinary cellular jitter on a phone would resize a desktop Mac's `nvim` session.
- **The infinite/pan canvas UI (§6) was fully designed, substantially built, then retired** for a conventional tiled Session→Tab→split-tree layout — the single largest reversal in the whole doc set, walked back after shipping.
- **The full ghostty surface renderer (§1) was the original architecture and was fully deleted**, in favor of the `libghostty-vt` parse-only approach — described in its own doc as "what has to go for the product to reach the surface it wants," i.e., a deliberate admission the original bet had hit a hard ceiling.
- **`uniffi-rs` was evaluated on request and rejected**, first on structural grounds and independently confirmed by a measurement, in favor of the tree's own hand-rolled FFI boundary discipline.
- **cbindgen was rejected** because it would need to run either inside `swift build` (structurally forbidden by the build's own rules) or as an awkward extra step.
- **A Chrome-extension-based automatic-update mechanism was considered and rejected** on churn/reliability grounds around its activation code.
- **A local dev-server preview pane opening Safari's Web Inspector was rejected** on two separate counts, one of them being a genuine security-boundary concern.
- **superd's original design (superd *holds* the fd but does not read it) was reversed mid-project** to "superd reads the master; only `read` moves" — a real correctness bug (§4's pre-ack-adjacent class of issue) forced the reversal: during the gap between hostd dying and a new one adopting, *nobody* was draining the kernel PTY buffer, and once it filled the child process itself blocked.
- **A herdr-style deferred-clear on agent disconnect (hold teardown briefly hoping the agent respawns) was rejected.**
- **Generic AX-based (accessibility-tree) detection of junk/non-real windows for the remote-desktop window list was tried twice and rejected twice** (once on an alpha-channel heuristic dead end, once on a "hidden app" heuristic that would have also hidden real windows like Parsec's own) — replaced with a small curated per-app name exclusion list, on the explicit reasoning that "a curated name list is the honest tool for a curated-junk problem."
- **Two full-project reset/re-scope events happened on 2026-07-04 alone** (a "minimalist reset" removing an entire decoration layer, then hours later a "full reset to the otty shell" that walked back the split-workspace and native-chrome-migration work done since) — worth noting as evidence that this project's process tolerated large, fast, admitted reversals rather than sunk-cost-protecting earlier UI decisions.

## 10. GPUI

A single mention exists in the entire slop-desk tree, in `docs/68-terminal-surface-in-rust.md` §7 ("What this does NOT touch"):

> "The framework ruling. AppKit/UIKit for the view layer, chosen 2026-08-31 and not reopened here. **GPUI is not in this tree and does not enter it.**"

That is the complete extent of it — no evaluation, no comparison, no rejected-alternatives entry anywhere in `DECISIONS.md` or any `decisions/vol-*.md` volume. GPUI was never seriously considered as an alternative to AppKit/UIKit for slop-desk; the project's UI framework choice was made once (2026-08-31, in favor of native AppKit/UIKit) and never revisited. This means Slopty's decision to build on GPUI is **genuinely new ground with no prior-art baggage or reversal risk to inherit from this codebase** — none of the knowledge above says anything for-or-against GPUI specifically. Every rendering/latency/input-injection finding above (Metal instancing discipline, dirty-tracking shape, vsync-off default, CGEvent injection details, font-metrics-must-match-ghostty rules) is framework-agnostic and applies identically whether the eventual GPUI renderer talks to the same Metal layer AppKit did or a different one GPUI owns directly.
